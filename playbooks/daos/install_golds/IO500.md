# DAOS-enabled IO500 installation

Phase1 reuses `playbooks/shared/install_ior.yaml` with
`--with-daos=/usr` and IO500 DAOS/DFS linker flags. It uses the existing DOCA
Open MPI module, builds once on the first client, and distributes the build
to all clients. No shared installer or other system's options are changed.
The existing phase6 native MPI test is unchanged.

From the generated Makefile directory on an allocated client:

```sh
make phase1-clean phase1
source /etc/profile.d/modules.sh
module load mpi/daos-doca-openmpi
ior -h | grep DFS
mdtest -h | grep DFS
ldd "$(command -v io500)" | grep -E 'libdaos|libdfs|not found'
```

Phase1 checks capabilities and library resolution on every client without
benchmark data I/O. It prints:

    PASS: IO500, IOR, and mdtest linked to DAOS; DFS API enabled.

The library paths must resolve, with no `not found` entries. Help and linker
reports are saved in `/usr/local/src/io500_daos-doca-openmpi/` as
`daos-{ior,mdtest}-help.txt` and `daos-{io500,ior,mdtest}-ldd.txt`.
An older build lacking DAOS support is invalidated before the shared rebuild.

DFS is IO500/IOR's direct DAOS file API backend, not a dfuse mount. This
step only builds that backend; configuring IO500 containers, workloads and
find support belongs to the subsequent run-playbook changes.

## Direct DAOS IO500 execution

With `system.type: daos`, `system.access: api`, and
`playbooks.cluster_test: ./playbooks/shared/io500_tester.yaml`, the shared
runner selects DOCA MPI only and configures the global DFS API for IOR,
mdtest, and IO500's directory operations. The data directory is a DFS
namespace path; results remain ordinary files in result_dir. No mount is used.

Phase1 now also builds `/usr/local/bin/tessi-io500-dfs-find`. Rerun phase1
before the first IO500 test. This external helper traverses DFS directly,
implements the find phases' name/byte-size/newer filters, and returns
`MATCHED count/total`. It uses one process and does not measure parallel-find
scaling. Each run creates a new POSIX-layout DAOS container solely for IO500;
it is deleted on success or failure. The existing api container is untouched.

The run preserves its INI, MPI output, engine membership before/after, and
pool-space snapshots before, after, and after cleanup. Existing shared IO500
result summaries and network counters are reused; kernel disk counters are
omitted for VFIO-managed DAOS storage. Other filesystem paths and MPI
selection are unchanged.

Bootstrap again if the test-playbook config changed, then use the printed
Makefile:

```sh
make -f /path/to/artifacts/Makefile phase1-clean phase6
```

The existing `io500.ppn` and `io500.stonewall_time` inventory options still
apply. The default stonewall is 300 seconds; a shorter diagnostic run is not
a standard IO500 submission. A long run may need a larger DAOS pool even
though containers are cleaned between runs.

### Current diagnostic mode: mdtest only, 30-second stonewall

DAOS-API enables mdtest easy/hard phases only. IOR, find, and mdworkbench
are disabled. The stonewall default remains 30 seconds, configurable through
`io500.stonewall_time`. Stat, read, delete and stonewall balancing can take
longer. This partial shortened run is not a standard IO500 submission.

### Independent pool capacity settings

Edit the clearly marked POOL CAPACITY block in
`playbooks/daos/configure_cluster/vars.yaml`:

- `daos_pool_metadata_gib_per_server`: **78 GiB per storage server**.
- `daos_pool_data_gib_per_server`: **155 GiB per storage server**.

Each server has one engine. Four servers therefore allocate **312 GiB
metadata (~335 GB)** and **620 GiB data (~666 GB)**. These are physical pool
allocations; replication reduces usable logical data capacity. Metadata no
longer grows as a fraction of the data allocation. The engine metadata
RAM-disk limit remains 112 GiB per server with `--mem-ratio=100%`.

For inventory overrides, use the same names without `daos_` under
`system.daos`: `pool_metadata_gib_per_server` and `pool_data_gib_per_server`.
Legacy `pool_size` and `pool_tier_ratio` overrides are rejected. The memory
limit can still be overridden with `system.daos.scm_size`.

Run `make phase5-clean all` to delete only the configured benchmark pool
(default `tessi`, including its containers), stop services, and recreate it
with the new capacities. Saved result directories are preserved. Phase5
prints the requested capacities and checks actual metadata and data sizes
independently, with a two-percent allocation-rounding tolerance; an old
pool cannot silently pass because it happens to have the same ratio.

If cleanup cannot contact already-stopped servers, it reports that no pool
was deleted. Initialized engines permit metadata-memory growth, or a size
correction on an empty RAM disk; other topology changes remain rejected.
